# Evals — Sun Protector

## Golden dataset

`evals/golden_dataset.json` — 30 hand-picked scenarios, generated by
`evals/generate_golden_dataset.py`. Each is a
`(phototype, uv_index, minutes_outside, minutes_since_last_spf, sweating_or_swimming)`
tuple with an `expected_risk_band` / `expected_reapply_due`.

**Coverage rationale** (why these 30, not a random sample):
- All 6 Fitzpatrick phototypes appear at least twice.
- Every risk-band threshold boundary is tested explicitly (UV exactly 3, 6, 8, 11 —
  `t11`-`t14`), since off-by-one errors at band boundaries are the most likely
  place the formula breaks silently.
- Reapplication edge cases: sunscreen applied fresh, overdue, and *exactly* at the
  120-minute boundary (`t15`-`t17`); no sunscreen applied yet at both low and high
  UV (`t18`-`t19`).
- Swimming/sweating halves the reapply interval — tested fresh vs. overdue under
  the 60-minute rule (`t20`-`t21`).
- Extremes: UV index 0 (night/heavy overcast, `t10`) and UV index 12-13 with the
  most burn-prone skin (`t7`, `t24`, `t30` — worst case).
- Realistic composite scenarios (beach day, commute, midday sport) rather than
  only synthetic boundary values, so the dataset isn't purely adversarial.

`expected_risk_band`/`expected_reapply_due` are computed *from the same formula*
documented in `SKILL.md` / `app/graph/risk.py` — this makes the dataset a
**regression guard on the formula's behavior**, not an independent check of it.
The independent check is the LLM-as-judge metric below, which scores free-text
advice against the scenario, not the formula's own output.

## Metrics

Run: `python evals/run_evals.py` → writes `evals/results/results.json`.

1. **`accuracy`** — does `risk.py`'s `risk_band`/`reapply_due` still match the
   golden dataset. This catches accidental regressions to the formula (e.g. an
   off-by-one at a band boundary) — it is *not* a check of whether the formula
   itself is medically "correct" (there's no ground truth for that beyond the
   cited guideline sources).
2. **`avg_judge_score`** (LLM-as-judge, 1-5, via `claude-haiku-4-5` → `gpt-4o-mini`
   fallback) — scores the *generated natural-language advice* for correctness
   and safety against the expected risk band. This is the metric that actually
   exercises the LLM, not just the deterministic formula.

**Latest run** (2026-09-22, `gpt-4o-mini` used throughout due to the Anthropic
key being out of credit at build time — see "Fallback in practice" below):

```
n = 30
accuracy = 1.0
avg_judge_score = 4.27 / 5   (normalized: 0.853)
```

**What these metrics do *not* show:** `accuracy` is trivially 1.0 by
construction (the dataset was generated from the same code it's checking) — it
only proves the formula hasn't silently changed, not that the formula is right.
`avg_judge_score` is a single LLM's opinion, scored at low `max_tokens` for
cost, and — as the A/B test below shows — has real run-to-run variance (~0.4-0.5
points at n=30) even with `temperature=0`. Neither metric checks the route-shade
tool, the RAG citations' relevance, or the human-in-the-loop confirmation flow;
those were verified manually (see README's "Manual verification" section) and
would need their own eval harness to automate properly — noted as future work.

## A/B experiment: does injecting the precomputed risk into the prompt matter?

Run: `python evals/ab_test.py` → writes `evals/results/ab_test_results.json`.

**Hypothesis.** The first version of the advice prompt (`v1_raw_inputs`) gave the
LLM only the raw inputs (phototype, UV, minutes outside, ...) and asked it to
reason about sunburn risk *itself*. Skimming the first eval run's transcripts
turned up a real, concrete miss:

> **t6_high_uv_type5** — phototype 5, UV 7, 30 min outside, no sunscreen yet.
> `expected_risk_band = "high"`. The `v1` prompt's advice: *"риск солнечного
> ожога умеренный"* (**moderate**) — visibly wrong against the app's own
> formula, because the LLM was doing its own ad hoc risk arithmetic instead of
> using `risk.py`'s output.

Hypothesis: passing the **precomputed** `risk_band`/`risk_ratio`/`reapply_due`
into the prompt (`v2_risk_injected` — this is what `compose_response` actually
does in production) should reduce this class of error, since the LLM only has
to *phrase* the risk, not compute it.

**What was compared.** Same model (Claude → gpt-4o-mini fallback), same golden
dataset, same judge rubric; only the prompt template differs.

**Result** (2026-09-22 run):

| Variant | avg judge score | avg latency |
|---|---|---|
| v1 — raw inputs, LLM infers risk | 4.33 / 5 | 2.07s |
| v2 — precomputed risk injected | 3.87 / 5 | 1.95s |

**This is the honest, slightly awkward result:** on raw average judge score
alone, v1 did *not* score lower in this run — it scored marginally higher,
inside what we now believe is judge noise (see below). Taken at face value that
contradicts the hypothesis.

**Why we still shipped v2 to production** (`app/graph/nodes.py:compose_response`
uses the risk-injected prompt): the judge score is a coarse proxy that doesn't
reliably penalize a *categorically wrong risk band* the way the t6 example
shows — the judge sometimes rates confident-but-wrong advice acceptably fluent.
v1 has no correctness guarantee: it can silently disagree with the app's own
formula, which is a safety-relevant failure mode a single scalar metric hides.
v2 cannot make that specific class of error by construction, because the model
is only asked to phrase a number it was already given, not derive it. We traded
a marginal, noisy judge-score difference for a hard correctness guarantee on
the one thing (risk band) the rest of the system's logic (branching, urgent
alerts) depends on.

**Caveat we're not hiding:** re-running `run_evals.py` (which also uses the v2
prompt, but with a slightly different judge phrasing) produced a materially
different average (4.27 vs. this run's 3.87 for the same prompt style) — a
~0.4 point swing from judge-prompt wording and model sampling alone at n=30.
**Conclusion: at this sample size, judge-score differences under ~0.5 should be
treated as noise, not signal.** A production version of this eval would (a) use
one canonical judge prompt everywhere, (b) average multiple judge samples per
case, and (c) grow the golden dataset past 30 — noted as follow-up work, not
done here in the interest of shipping.

## Fallback in practice

During this build, the Anthropic API key had a zero credit balance (see the
first real call in the session logs: `AnthropicInvalidRequestError: Your
credit balance is too low...`). Every single LLM call in this document — evals,
A/B test, and the live demo — therefore actually exercised
`config.call_with_fallback()`'s fallback path to `gpt-4o-mini` in production,
not in a simulated test. This is unplanned but useful evidence that the
"fallback strategy between models" (bonus requirement) works under a real
failure, not just a mocked one. Once Anthropic credit is topped up, `model_used`
in every API response will read `claude-sonnet-5` instead of the `(fallback,
primary_error=...)` tag, with no code changes needed.
